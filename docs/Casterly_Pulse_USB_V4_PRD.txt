1. Executive Summary
Casterly Pulse USB V4 is an enterprise-grade, bootable hardware inspection platform engineered for high-volume ITAD (IT Asset Disposition) workflows. It enables field technicians and warehouse operators to perform fully automated, repeatable hardware diagnostics and physical grading of laptops without installing any software on the device under inspection.
The platform runs from a custom bootable USB drive built on Ubuntu 26.04 LTS. The application is built with Tauri v2 — a framework combining a Rust backend with a React TypeScript frontend. All hardware data is collected through native Linux kernel interfaces and command-line tools. Results are stored in an embedded SQLite database and queued for cloud synchronization to Supabase.

4. System Architecture
4.1 Overview — Tauri v2 Desktop Architecture
Casterly Pulse USB V4 is built on Tauri v2, a framework that embeds a Rust binary as the application backend and renders a React TypeScript web application in a platform-native WebView. The two layers communicate exclusively via Tauri's invoke() IPC bridge — the frontend calls named Rust commands and receives serialized JSON responses.
4.2 Technology Stack
4.3 Tauri IPC Bridge — Rust Commands
All communication between the React frontend and the Rust backend flows through Tauri's invoke() IPC mechanism. The frontend calls a named command string; Tauri routes it to the corresponding #[tauri::command] function in Rust. The result is serialized as JSON and returned to the frontend as a TypeScript Promise.
4.4 Parallel Scan Architecture
The SystemScan screen fires all 9 invoke() calls concurrently on component mount — none await the previous. Each call resolves or rejects independently, updating a local state slice and incrementing a completedCalls counter. When completedCalls reaches the total (currently 9), the workflow auto-advances. This parallel architecture means scan time is bounded by the slowest single collector, not the sum of all.
4.5 Scan Caching — InspectionContext
InspectionContext is a React Context provider wrapping the entire application. It stores scan results, scan state, and inspection metadata across all workflow screens. When the user navigates back to SystemScan from a later screen, the component detects data.scanCompleted === true, restores all state from context, and sets completedCalls to 9 immediately — skipping all invoke() calls. This ensures collectors never run twice per inspection.
// InspectionContext.tsx — shared data structure across all workflow steps
interface InspectionData {
  systemInfo:   SystemInfo | null;    // From get_system_info
  cpuInfo:      CpuInfo | null;       // From get_cpu_info
  memoryInfo:   MemoryModule[];       // From get_memory_info (array)
  storageInfo:  StorageDevice[];      // From get_storage_info (array)
  batteryInfo:  BatteryInfo | null;   // From get_battery_info (null = no battery)
  networkInfo:  NetworkInfo | null;   // From get_network_info
  displayInfo:  DisplayInfo | null;   // From get_display_info
  gpuInfo:      GpuInfo[] | null;     // From get_gpu_info (array)
  cameraInfo:   CameraInfo | null;    // From get_camera_info
  scanCompleted:bool;                 // Guard: true = use cached, skip collectors
  scanTimestamp:number | null;        // Unix ms timestamp of scan
  inspectionStartTime: number | null; // Unix ms of workflow start
}

8. Hardware Collectors — Deep Specification
8.1 Collector Architecture
Each hardware collector is a Rust module in src-tauri/src/inventory/. All collectors implement a collect() function returning Result<T>. The master collector (collector.rs) calls all 9 in sequence via collect_all() → DeviceInventory, but the Tauri command layer calls each individually to support the parallel invoke() pattern from the frontend.
8.2 System Collector (inventory/system.rs)
Data Sources
Strategy: sysfs paths are tried first (no root required, instant). If empty (permission denied or unavailable), falls back to dmidecode with sudo. This dual-path approach ensures maximum compatibility across OEM BIOS implementations.

8.4 Memory Collector (inventory/memory.rs)
Calls sudo dmidecode -t memory and parses the multi-block output. Each 'Memory Device' section in the output represents one physical slot. The parser maintains state across lines, flushing a complete MemoryModule struct when the next 'Memory Device' header is encountered.

8.5 Storage Collector (inventory/storage.rs)
Primary discovery via lsblk -d -b -P -o NAME,SIZE,MODEL,SERIAL,TRAN. The -P flag outputs key=value pairs; the -d flag shows disks only (no partitions); -b outputs sizes in bytes. USB transport devices are filtered out (boot media exclusion). NVMe vs SATA detection uses device path (/dev/nvmeX) and transport field.
Boot Media Exclusion
// storage.rs — USB transport exclusion
if transport.to_lowercase() == "usb" {
    continue;  // Skip USB devices — prevents testing the boot USB itself
}
// Also skip: loop, ram, sr (loop devices, ram disks, optical drives)
if name.starts_with("loop") || name.starts_with("ram") || name.starts_with("sr") {
    continue;
}

8.6 Battery Collector (inventory/battery.rs)
Scans /sys/class/power_supply/ for directories starting with 'BAT'. Reads Linux battery sysfs attributes directly — no external tools required. Supports two battery reporting modes found across different OEMs:
Unit Normalization: if value > 500,000 → divide by 100,000.0 (µWh → Wh). Otherwise divide by 1,000.0 (mWh → Wh). This heuristic handles the majority of OEM reporting variations seen in ITAD fleets.

8.7 BIOS Collector (inventory/bios.rs)
Calls sudo dmidecode -s <field> for each BIOS attribute. The -s flag returns a single string value for the specified DMI string keyword — simpler and faster than parsing the full -t bios output.
8.8 GPU Collector (inventory/gpu.rs)
Parses lspci output for lines containing 'VGA compatible controller' or '3D controller'. Extracts vendor (Intel/AMD/NVIDIA from string match), full model string, and PCI bus address (first whitespace token).
// gpu.rs — vendor detection from PCI description string
if line.contains("Intel") { vendor = "Intel" }
else if line.contains("AMD") { vendor = "AMD" }
else if line.contains("NVIDIA") { vendor = "NVIDIA" }
8.9 Display Collector (inventory/display.rs)
Scans /sys/class/drm/ for connector directories containing 'eDP' in the name (embedded DisplayPort — the internal laptop panel interface). Reads the raw EDID binary from <connector>/edid. Parses EDID bytes directly in Rust — no external tools.
EDID Binary Parsing

8.10 Network Collector (inventory/network.rs)
Combines lspci output for human-readable adapter names with /sys/class/net/ directory enumeration for interface names and MAC addresses. Bluetooth detection uses hciconfig command existence as proxy.
8.11 Camera Collector (inventory/camera.rs)
Calls v4l2-ctl --list-devices which outputs camera device names followed by their /dev/videoX paths. Parses lines containing 'Webcam', 'Camera', or 'Integrated'. First /dev/video* path after a device name is captured as the device node.

9. Functional Diagnostics Tests
9.1 Test Architecture
Functional tests are active tests requiring hardware interaction and technician judgment. Unlike passive collectors which run automatically, each test requires a technician to observe the hardware behavior and confirm PASS or FAIL. Results are stored in InspectionRun alongside the passive inventory data.
9.2 Keyboard Test (diagnostics/keyboard.rs)
Enables crossterm terminal raw mode to intercept all keystrokes before the OS processes them. A HashSet tracks unique keys seen. The crossterm event poll loop runs on 100ms intervals. Key names are normalized: Char(c) → character string, Enter → 'ENTER', Tab → 'TAB', Backspace → 'BACKSPACE', Esc → 'ESC', others → Debug format.
Exit Protocol
Q key pressed 3 times, each press within 1 second of the previous
q_count resets to 0 if any non-Q key is pressed or if >1 second elapses between Q presses
Prevents accidental exit from normal typing
// keyboard.rs — exit detection
if c == 'q' {
    let now = Instant::now();
    if let Some(last) = last_q_time {
        if now.duration_since(last) > Duration::from_secs(1) { q_count = 0; }
    }
    q_count += 1;
    last_q_time = Some(now);
    if q_count >= 3 { break; }  // Exit test
} else { q_count = 0; last_q_time = None; }
9.3 Speaker Test (diagnostics/speaker.rs)
Detects audio player availability using which command. Prefers ffplay for its no-display mode and autoexit flag. Falls back to aplay for environments without ffmpeg installed. Audio file: assets/speaker_test.wav — a stereo WAV designed to test left and right channel routing.
// speaker.rs — player selection
let player = if command_exists("ffplay") { "ffplay" } else { "aplay" };
// ffplay command: -nodisp (no video window) -autoexit (exit when audio ends)
Command::new("ffplay").args(["-nodisp", "-autoexit", "assets/speaker_test.wav"]);
// aplay command: simple WAV playback
Command::new("aplay").arg("assets/speaker_test.wav");

11. SQLite Database Schema
11.1 Database Overview
SQLite is used as the embedded database for Pulse V4. The database file is named udiag.db and is opened via rusqlite::Connection::open('udiag.db'). With the 'bundled' feature flag, rusqlite compiles SQLite directly into the Rust binary — no external libsqlite3.so dependency on the target machine.
11.2 Table: lots

11.3 Table: inspections
The json_data column stores the complete InspectionRun struct as a formatted JSON string. This includes all hardware inventory, manual grading, test results, and metadata. The choice to store as JSON (rather than normalized columns) allows schema flexibility as new hardware categories are added without database migrations.

15. User Experience Design
15.1 Design Principles
Kiosk-first: the application runs fullscreen in a controlled environment — all navigation is within the app
Dark-neutral theme: slate/white backgrounds with blue accent — professional, reduces eye strain in warehouse lighting
Card-based layout: each hardware category is an independent InfoCard with consistent header/body structure
Status badges: color-coded (emerald=OK, amber=warn, red=critical) for instant visual triage
Progressive disclosure: defect sub-types appear only when a component is marked FAIL
Auto-advance: SystemScan auto-advances without button press when all collectors complete
Large touch targets: all interactive elements ≥ 44px for warehouse glove compatibility
Keyboard navigation: all primary actions accessible without mouse
15.2 InfoCard Design System
The InfoCard component is the primary data display unit across the application. Used in SystemScan for all 10 hardware categories. Structure:
Header: Lucide icon (15px) + category title (text-sm) + status badge (text-[10px] rounded-full)
Body: key-value rows — label (text-xs text-slate-500) + value (text-xs text-slate-800 font-medium)

16. USB Build & Deployment
16.1 Build Architecture
The bootable USB is built using Cubic to customize an Ubuntu 26.04 LTS ISO. The Tauri application binary + React frontend bundle are embedded in the ISO. A systemd service auto-launches the application on graphical login. The ubuntu user is configured for auto-login to eliminate technician boot interaction.
16.2 Build Steps
Install Cubic on a build workstation: sudo apt-add-repository ppa:cubic-wizard/release && sudo apt install cubic
Download Ubuntu 26.04 LTS Desktop ISO from ubuntu.com
Launch Cubic: select source ISO, configure project directory
Build the Tauri application on a Linux host (must be Linux -- a Windows/WSL build
produces udiag4.exe, which will not run inside this Ubuntu image):
npm install && npm run tauri build
# Produces: src-tauri/target/release/udiag4 (binary; frontend is embedded in it,
#           dist/ does not need to be copied separately)
Copy udiag4 and resources/audio/speaker_test.wav (from src-tauri/resources/audio/,
preserving that folder structure) into the Cubic chroot (e.g. /root/casterly-pulse-build)
In the Cubic virtual environment terminal, run packaging/install.sh (also copied into the chroot alongside packaging/casterly-pulse.service).
This single script installs the runtime dependencies (v4l-utils, ffmpeg, smartmontools,
nvme-cli, lshw, dmidecode, usbutils, pciutils, bluetooth, bluez), copies the app to
/opt/casterly/pulse/, installs + enables casterly-pulse.service, and configures GDM3
auto-login for the ubuntu user. See packaging/casterly-pulse.service for the unit
definition (note it sets WorkingDirectory=/opt/casterly/pulse, since udiag.db and
exports/ are opened via relative paths and would otherwise land at "/").
Exit Cubic virtual environment, generate ISO
Write to USB: sudo dd if=casterly-pulse-v4.iso of=/dev/sdX bs=4M status=progress
Note: if the ISO is dd'd without a persistence partition, anything the app writes to
/opt/casterly/pulse at runtime (udiag.db, exports/) will not survive a reboot unless
persistent storage is configured for that path during the ISO build.

[TABLE 39]
Upload Queue (SQLite: upload_queue WHERE status='PENDING')
     │
     ▼
Sync Engine (src-tauri/src/upload/)
  1. Check network connectivity
  2. Fetch PENDING records from upload_queue
  3. For each record:
     a. Load inspection JSON from inspections WHERE uuid = ?
     b. POST to Supabase REST API /rest/v1/inspections
     c. Include headers: apikey, Authorization: Bearer, Content-Type: application/json
     d. On HTTP 200/201:
        → UPDATE upload_queue SET status='UPLOADED', uploaded_at=now()
        → UPDATE inspections SET uploaded=1
     e. On failure:
        → UPDATE upload_queue SET status='FAILED', retry_count=retry_count+1
        → Exponential backoff: 2^retry_count seconds
     f. Max retries: 5 → status='FAILED' (requires manual retry)
  4. Signal SyncStatus screen with results
